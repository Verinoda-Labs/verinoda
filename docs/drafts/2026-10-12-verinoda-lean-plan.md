# Verinoda Lean Implementation Plan (D186)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the Verinoda Lean design: analyze and history_search return small, honest, lead-shaped MCP responses; history is correct where git is blind; the mod keeps tools-in-front, the call rule and freshness and loses the rest; the package loses the upstream CLI surface, the LLM layer and the scipy dependency; the security findings are closed; the re-runs are made.

**Architecture:** The analysis engine (`verinoda/analysis.py`, `history.py`) keeps its result dicts; the MCP layer (`verinoda/mcp/server.py`, `analysis_view.py`) builds compact responses from them. Git goes through one funnel (`verinoda/gitexec.py`); paths from any index or store go through one containment helper (`verinoda/paths.py`). The mod (`claude-mods/verinoda-live`) shrinks to tools-in-front, a prompt section and freshness.

**Tech Stack:** Python 3.10+ (pytest, ruff), TypeScript mod under Claude Code's plugin API (`claude plugin test`, `tsc`), git.

**Spec:** `docs/drafts/2026-10-12-verinoda-lean-design.md` (sections cited as §N below). Read it first; it carries the measured reasons.

## Review Focus

1. A `needs_clarification` or `invalid_plan` analyze result (clarifications, errors) still reaches the model through the new lead shape; the budget never cuts them. Test in Task 2.
2. A why-question on a file whose symbol history times out (`VERINODA_MCP_GIT_TIMEOUT` exceeded) returns `status: partial` with what was searched, not a tool error, and the model still gets the leads it had. Test in Task 3.
3. A repository that is a subfolder of its git work tree keeps its CODEOWNERS evidence verifiable (root = work-tree top) while a root symlinked outside the repository is `gone`. Test in Task 5.
4. A hostile repository that ships `verinoda.exe` or `python.exe` at its root, a `.venv/`, or a `.verinoda/` folder: the mod runs none of them at session start. Test in Task 1 (Windows test with a fake executable in the root).
5. After the deletions, `verinoda scan`, `verinoda update` and `python -m verinoda.benchmark run` still import and run (detect.py and export.py imported the deleted modules at module top). Test in Task 6.
